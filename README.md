# Habit Tracker — пробная версия 0.2.3

Telegram-бот на `python-telegram-bot`. Основа — исходный архив Habit-Tracker-main; интерфейс и логика переработаны для тестового релиза.

## Исправление 0.2.3: PostgreSQL и восстановление исчезнувших привычек

**Самый безопасный порядок действий — сначала диагностика, затем восстановление.**
На хостинге и компьютере используй одну и ту же строку `DATABASE_URL`, если хочешь
видеть одни данные. Не публикуй эту строку, пароль БД и `BOT_TOKEN`.

### Что было не так

В версии 0.2.1 снимок данных записывался под хешем **всего токена** бота.
В версии 0.2.2 ключ изменился на хеш **числового ID бота**. Если токен
перевыпустили до обновления, старый ключ невозможно определить из нового токена.
Если 0.2.2 успела сохранить пустой снимок под новым ключом, автоматический импорт
старого снимка не запустится: новая запись уже существует. При этом старая
запись в PostgreSQL обычно остаётся нетронутой.

Версия 0.2.3 **не удаляет** старые строки. Если ключ текущего бота не найден,
но другие снимки есть, бот по умолчанию **не создаёт молча пустое хранилище**.
Вместо этого он выводит подсказку о диагностике. Для намеренно нового бота
в общей базе можно установить `HABIT_ALLOW_NEW_STORE=1`. Другие случаи:

- Если в таблице нет ни одной записи, версия выдаёт предупреждение: проверь
  правильность `DATABASE_URL`. Если это рабочая база и она должна содержать
  данные, добавь `HABIT_REQUIRE_EXISTING_DATA=1`, тогда пустая база блокирует запуск.
- Если `DATABASE_URL` отсутствует, работает локальный `.pkl`. Теперь путь к
  относительному `.pkl` ищется и в папке проекта, и в прежней рабочей папке.
  Если оба файла есть, бот требует выбрать один явным абсолютным `DATA_PATH`.

### 1. Безопасная диагностика — ничего не меняет

Поставь зависимости, но прежде чем восстанавливать данные, **останови бота
на хостинге и локально**, чтобы он не продолжал сохранять новые пустые снимки.
Открой терминал в папке проекта и выполни:

```bash
python -m pip install -r requirements.txt
python db_recovery.py
```

Команда только читает PostgreSQL и печатает таблицу:
`KEY / BYTES / LAST_UPDATED / TYPE`.

- `CURRENT` — запись, которую загружает v0.2.3 сейчас.
- `LEGACY_CURRENT_TOKEN` — запись версии 0.2.1 с тем же токеном.
- `OTHER_OR_OLD_TOKEN` — запись с другим ключом: это **может быть** старая
  запись после замены токена, а может быть **другой бот** в общей базе.
- Размер и дата помогают выбрать источник, но **не доказывают принадлежность**.

Если выводится «локальное файловое хранилище» — переменная `DATABASE_URL`
не активна. Если «нет подключения» — проблема с сетью или учётными данными,
а не с ключом снимка. Если таблица отсутствует, проверь, ту ли БД подключили.

### 2. Восстановление конкретного старого снимка

**Перед изменениями сделай резервную копию базы в панели хостинга.**
Убедись, что старый `KEY` принадлежит именно этому Habit Tracker.
Можно отдельно выгрузить его в `.pkl` (в этом файле личные данные, не публикуй его):

```bash
python db_recovery.py --export СТАРЫЙ_KEY backup_habit.pkl
```

Если строки `CURRENT` **нет**, запусти:

```bash
python db_recovery.py --recover СТАРЫЙ_KEY
```

Если строка `CURRENT` **есть, но это пустая/неправильная версия**, и ты
сознательно решил её заменить, запусти:

```bash
python db_recovery.py --recover СТАРЫЙ_KEY --replace-existing
```

Во втором случае инструмент сначала сохраняет прежнюю активную запись как
**отдельную резервную строку** с ключом `bkp...`, затем копирует выбранную.
Исходная старая строка сохраняется всегда. Все действия выполняются в одной
транзакции PostgreSQL. После восстановления убери временные флаги
`MIGRATE_SINGLE_LEGACY_ROW` и `HABIT_ALLOW_NEW_STORE`, запусти бота, проверь
`/start`, `/trackers`, отметки и сохранение после перезапуска.

**Важно:** не надо автоматически восстанавливать запись с максимальным размером
или последней датой — она может относиться к другому боту. Если есть сомнения,
выполни только `python db_recovery.py` и пришли вывод (без `.env` и токенов).

## Исправления и тесты 0.2.2: сеть Telegram и ротация токена

На этой версии проводились дополнительные автономные проверки сетевых ошибок.
В логах от `httpx` больше не должно быть полных URL Bot API с токеном;
`httpx`/`httpcore` переведены на уровень WARNING и добавлен фильтр секретов
для стандартного консольного логгера. Зарегистрирован `Application.add_error_handler()`;
сетевые `NetworkError/TimedOut` больше не печатают огромные трассировки при
отправке ответа на кнопку. Настройки `connect_timeout` подняты до 25 секунд
для отправки сообщений и `getUpdates`. **Это не решает неисправный прокси** —
если TLS-соединение не устанавливается, нужно проверить VPN/прокси/сеть на самой машине.

Данные PostgreSQL теперь записываются под устойчивым ключом из **числового Telegram ID бота**,
а не под хешем всего токена. Существующее хранилище версии 0.2.1 с **тем же токеном**
мигрирует автоматически. При замене токена *до обновления кода* старую запись по
хешу предыдущего токена невозможно надёжно определить в базе с несколькими ботами.
**Устаревшее примечание о миграции 0.2.2:** раньше использовался
`MIGRATE_SINGLE_LEGACY_ROW=1`. Он работает только если в таблице один
старый снимок и нет новой активной строки. При двух строках он не помогает.
В 0.2.3 рекомендуемый путь — `python db_recovery.py` и восстановление
конкретного снимка после резервного копирования, как описано выше.

**Результат проверок в среде сборки:** `python tests_smoke.py` — 17/17,
`python tests_persistence.py` — 8/8, `compileall` без ошибок.
`tests_runtime.py` предназначен для запуска в окружении с установленным настоящим
`python-telegram-bot`: здесь этот пакет отсутствует. Реальный API Telegram и
подключение к твоему хостингу отсюда не проверялись.

### Диагностика Telegram-соединения

Если `getUpdates` получает 200, но `sendMessage` выдаёт `ConnectTimeout` в
`httpcore._async.http_proxy`, это сбой сетевого TLS-соединения через прокси,
а не подтверждение ошибки в кнопке. На Windows проверь переменные `HTTPS_PROXY`,
`HTTP_PROXY`, `ALL_PROXY` **без публикации их значений** и наличие рабочего VPN/прокси.
Не запускай одновременно локальную и хостинговую копии polling-бота с одним токеном.

Если сообщение в чат *фактически* ушло, а ответ сервера потерялся на таймауте,
Telegram может доставить дублирование при повторной попытке: полностью
гарантировать «ровно одно сообщение» при нестабильной сети без подтверждения
от Telegram невозможно.

**После появления токена в чужих логах или переписке перевыпусти его через
BotFather и обнови `.env`; не выкладывай токен ни в каких следующих логах.**

## Исправление 0.2.1: ошибка `Invalid argument` с PostgreSQL

В 0.2.0 бот мог ошибочно попытаться открыть URL `postgresql://...` как имя файла
через `PicklePersistence`, что на Windows приводило к `OSError: [Errno 22] Invalid argument`.
Теперь поддерживаются **два режима** (автоматический выбор):

1. **Локально (файл):** `DATA_PATH=bot_data.pkl`, `DATABASE_URL` отсутствует/пустая.
2. **На хостинге (PostgreSQL):** `DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DBNAME`.
   В режиме PostgreSQL `DATA_PATH` не используется для дальнейшего сохранения,
   но его локальный файл может быть один раз импортирован при переходе на PostgreSQL.

**Совместимость:** если в `DATA_PATH` по ошибке указан URL PostgreSQL,
0.2.1 сама распознаёт его и включает PostgreSQL-режим, не передавая адрес в `PicklePersistence`.
Но правильно указать URL через `DATABASE_URL`, а `DATA_PATH` оставить файлом.

PostgreSQL должен быть доступен из среды запуска (настройки сети, логин и пароль).
Схема `habit_tracker_state` создаётся автоматически. В версии 0.2.1 данные разделялись по хешу полного токена.
Начиная с 0.2.2 используется числовой ID бота; см. восстановление выше. Если таблица пустая и рядом лежит **твой
собственный доверенный** `bot_data.pkl`, он будет импортирован при первом запуске.
Если запись в PostgreSQL не удалась, бот выдаст ошибку, вместо скрытого перехода
на непостоянный локальный файл. При рестарте сохранённое состояние загружается из PostgreSQL.

После обновления зависимостей запускай `python -m pip install -r requirements.txt`.
Для проверки без сети: `python tests_smoke.py`, `python tests_persistence.py` и `python tests_runtime.py` (при установленном Telegram SDK).

**Безопасность:** никогда не отправляй строку подключения в чат, логи, публичный GitHub
или скриншоты. Если пароль уже был опубликован, замени его на сервере и в `.env`.
На сервере должна работать **только одна копия** polling-бота: PostgreSQL сам по себе
не защищает от двух параллельных запусков, дублирующих Telegram-уведомления.

## Что включено

- Первичная настройка языка и часового пояса **только один раз** (при `/start`).
- Привычки: название, дни недели, время напоминания или «нет». Повторного запроса города нет.
- Отметки **выполнено / не выполнено / пропущено** за текущую локальную дату.
- Серия считается по *запланированным дням*, выходные/неактивные дни не обрывают её.
- В **00:00 по местному времени** прошлый запланированный день без отметки считается невыполненным. При отключении бота пропущенные дни будут обработаны при следующем запуске/обращении пользователя. Календарная история сохраняется, обнуляется **серия**, не история.
- Исправлена цепочка кнопок «Назад»: настройки, список → карточка → редактирование / удаление, цели сегодня → карточка, этапы создания.
- Админ-панель по модели погодного бота: общая рассылка, личное сообщение, список пользователей с карточками, повышение/понижение уровня, создание ADV-ключей, статистика, экспорт/импорт JSON.
- Команда `/k КЛЮЧ` или **Настройки → Активировать ключ ADV**. Сгенерированные в админке ключи одноразовые. `ADV_ACTIVATION_KEYS` из `.env` — необязательные **многоразовые** ключи для совместимости с погодным ботом.
- Бесплатный режим **Free** без ограничений на число привычек. **ADV** пока лишь уровень доступа, отдельные платные функции не назначены. Встроенного приёма платежей нет.

## Запуск

1. Используй Python **3.10+** (рекомендуется 3.11/3.12) и установи зависимости:
   ```bash
   python -m pip install -r requirements.txt
   ```
2. Скопируй `.env.example` в `.env`, подставь `BOT_TOKEN`, `ADMIN_ID` и `WEATHER_TOKEN` (для поиска города). Токены не публикуй в репозитории.
3. Запуск:
   ```bash
   python main.py
   ```
4. Проверка без Telegram и секретов:
   ```bash
   python tests_smoke.py
   ```

## Важно для хостинга и уведомлений

- Бот должен работать в **постоянном worker / background service** (не как временный HTTP-запрос, который хостинг «усыпляет»). Если процесс остановлен, Telegram-бот не может физически посылать напоминания.
- `JobQueue` запускает проверку каждые **30 секунд**, включая первый запуск. Проверка идёт по локальному времени каждого пользователя, без потери расписания после перезапуска. Напоминание отправляется максимум один раз за дату, если время наступило не более **30 минут назад**. Более старые уведомления не догоняются задним числом.
- **Обязательно постоянное хранилище**: используй PostgreSQL (`DATABASE_URL`) либо укажи `DATA_PATH=/path/to/persistent-volume/bot_data.pkl` на постоянном диске. Обычный временный диск хостинга после перезапуска может быть очищен.
- Если на сервере одновременно запущены **две копии** одного polling-бота, они могут мешать друг другу и дублировать сообщения. Запускай одну.
- Название города использует OpenWeatherMap. По координатам `timezonefinder` определяет IANA-зону, поэтому для городов обычно корректно учитывается зимнее/летнее время. Если пользователь ввёл числовой UTC-сдвиг, это **фиксированный** сдвиг, без авто-перехода.
- Чтобы пользователь получал сообщения, он должен начать диалог с ботом и не блокировать его.

## Безопасное обновление с прежней версии

1. Останови старый процесс бота и **сделай резервную копию `bot_data.pkl`**.
2. Подмени Python-файлы, но **не удаляй свой `bot_data.pkl`** и реальные переменные окружения.
3. Запусти и проверь `/start` и сохранённые трекеры на своём аккаунте. Старые настройки языка, часового пояса и истории подхватываются.
4. После миграции прошлые запланированные дни без отметок для старых привычек будут закрыты как невыполненные **начиная с первой сохранённой даты в истории**. Для совсем пустой старой истории неизвестна фактическая дата создания, поэтому прошлое не выдумывается.
5. Старый текстовый формат экспорта `USER:/TRACKER:` заменён на JSON. Данные `bot_data.pkl` продолжают читаться; если у тебя есть только текстовые архивы, их нужно отдельно конвертировать.

**Не используй скачанный архив как единственную копию данных с реального бота.** В ZIP не включены настоящие токены и `bot_data.pkl`.

## Команды

- `/start` — настройка (для новых пользователей) / главное меню.
- `/today` — цели на сегодня.
- `/trackers` — список привычек.
- `/add_tracker` — новая привычка.
- `/settings` — настройки.
- `/k КЛЮЧ` — активировать ADV.
- `/admin` — панель владельца.
- `/cancel` — отменить ввод и выйти в меню.

## Известные ограничения тестового релиза

- **Нет проведённого теста с живым Telegram API и на твоём хосте**: проведены компиляция и автономные проверки. Проверь доставку уведомлений после деплоя.
- ADV пока **не даёт отдельных функций**, кроме фиксации статуса, которым управляет админка.
- Отправка напоминаний не работает в период выключения/сна сервера и не компенсирует простои более 30 минут.
- Режим PostgreSQL хранит единый сериализованный снимок в `BYTEA` (для пробного запуска). Для большой пользовательской базы нужна полноценная нормализованная схема данных и отдельный журнал отправок. PostgreSQL-режим проверен автономными тестами с имитацией базы, но пока не тестировался на реальном сервере.
